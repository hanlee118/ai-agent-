# Agent Team 研发执行协议 v1

更新时间：2026-04-04

## 适用范围

适用于 `DESIGN`、`DEV`、`ACCEPT` 阶段，覆盖从方案形成到实现、验收、回填的下半程协作。

## 目标

让设计、研发、测试与验收形成可交接、可验证、可回填的执行闭环。

## 角色分工

1. `ROLE_PRODUCT`
   - 负责体验目标、范围优先级、验收口径
2. `ROLE_DESIGN`
   - 负责结构、视觉、交互、状态与响应式方案
3. `ROLE_ARCH`
   - 负责技术方案、边界契约、接口与风险
4. `ROLE_DEV`
   - 负责实现、联调、回归与交付
5. `ROLE_QA`
   - 负责验证、验收、回填与归档

## 下半程总原则

1. 先有契约，再做实现。
2. 先有交接，再做下游执行。
3. 先有验证，再判定完成。
4. 设计优先技能驱动，研发优先工具驱动。
5. 不允许用旧项目模板替代当前项目设计与实现判断。

## DESIGN 协议

### 阶段目标

把分析结论转成可直接交给研发实现的设计方案。

### 必做事项

1. 明确体验目标、页面范围、内容优先级。
2. 完成信息结构、关键页面、关键状态和交互方案。
3. 说明响应式规则、边界状态和异常状态。
4. 标注哪些来自已确认事实，哪些来自合理假设。

### 标准产物

1. 页面/模块结构方案
2. 视觉与交互说明
3. 关键状态说明
4. 响应式与异常状态规则
5. 研发交付边界

### DESIGN 门禁

以下任一缺失，不允许进入 `DEV`：

1. 关键页面或状态未定义
2. 交互规则不完整
3. 设计约束不清
4. 输出无法直接指导研发实现

## DEV 协议

### 阶段目标

基于设计与架构契约完成真实实现、联调和验证。

### 必做事项

1. 先明确技术方案、接口、依赖和风险。
2. 再通过终端工具完成代码修改。
3. 完成必要测试、联调和回归检查。
4. 记录改动范围、验证结果和遗留风险。

### 标准产物

1. 技术方案
2. 代码改动
3. 验证结果
4. 风险与遗留问题
5. 交给 QA 的回归关注点

### DEV 门禁

以下任一缺失，不允许进入 `ACCEPT`：

1. 无真实代码改动证据
2. 无验证结果
3. 关键风险未记录
4. 无法说明已完成与未完成边界

## ACCEPT 协议

### 阶段目标

完成验收、回填和长期记忆沉淀，关闭本轮项目闭环。

### 必做事项

1. 按验收标准检查结果。
2. 输出测试报告和验收结论。
3. 回填产品文档与长期记忆。
4. 明确项目是否可归档、是否可进入下一轮迭代。

### 标准产物

1. 测试报告
2. 验收结论
3. 产品说明文档回填
4. 长期记忆回填
5. 复盘项

### ACCEPT 门禁

以下任一缺失，不允许关闭项目：

1. 必需交付物不齐
2. `readyForAcceptance` 不成立
3. 验收结论不明确
4. 回填未完成

## 协作交接卡

下半程每个关键阶段都必须输出固定字段：

1. `factsConfirmed`
2. `assumptions`
3. `decisions`
4. `handoff`
5. `openQuestions`

要求：

1. `handoff` 必须能直接供下游角色执行。
2. `openQuestions` 必须保留真实风险，而不是空泛写“无”。

## 技能执行记录

关键阶段输出末尾必须追加：

1. `skillsUsed`
2. `reasoningBasis`
3. `artifactsProduced`
4. `verification`

要求：

1. 设计阶段优先真实设计技能。
2. 研发阶段优先终端、编辑、测试工具。
3. 验收阶段优先真实测试和核验结果。
4. 不允许伪造已执行的技能或验证。

## 记忆与模板协议

1. 长期记忆保持开启。
2. 仅允许当前项目或高关联经验参与设计、研发、验收。
3. 旧项目视觉模板、演示页、默认方案不得直接复用。
4. 若引用历史经验，必须服务于当前项目判断，而不是替代当前项目判断。

## 成功判定

满足以下条件才算真正完成：

1. 设计可实现
2. 研发可运行或可验证
3. 验收有依据
4. 回填可追溯
5. 下游 Agent 能无歧义接手

## 推荐执行方式

1. `ROLE_PRODUCT` 与 `ROLE_DESIGN` 先收敛方案与边界。
2. `ROLE_ARCH` 先沉淀实现契约。
3. `ROLE_DEV` 再做真实实现与验证。
4. `ROLE_QA` 最后做验收、回填和归档。
