# Agent 协作平台需求文档（最新）

> 版本：v1.2  
> 日期：2026-04-02  
> 适用仓库：`/private/tmp/ai-agent-check`

## 1. 文档说明

本文档是中文需求入口，和 [LATEST_REQUIREMENTS_SPEC.md](./LATEST_REQUIREMENTS_SPEC.md) 保持一致。  
若两者冲突，以 `LATEST_REQUIREMENTS_SPEC.md` 为准。

## 2. 本版本需求目标

- 建立可收敛的多 Agent 阶段推进流程。
- 建立真实模型强门禁，禁止 scripted/degraded 假通过。
- 建立角色级质量门禁（ROLE_PM + ROLE_DESIGN/ARCH/DEV/QA）。
- 建立 GitLab Harness 外部协同闭环。
- 建立可重复验收与一键健康检查体系。
- 建立“新建项目 -> 需求预览 -> 对齐确认 -> 项目推进”的可解释预填链路。
- 建立不会阻塞用户操作的审批返工链路。
- 明确本地验收入口，避免静态预览与实时前端混淆。

## 3. 核心需求清单（Must Have）

1. 项目推进必须支持风暴检测、退避与软恢复。  
2. 审批阶段必须执行真实模型门禁。  
3. 门禁失败必须返回可执行的 `requiredActions + recoveryPlan`。  
4. DEV/ACCEPT 阶段必须支持 GitLab issue 同步与 webhook 回写。  
5. 平台必须输出结构化验收与健康报告到 `docs/reports/`。  
6. 必须提供可重复通过的固定验收脚本路径（OCC-20260401-018）。
7. 新建项目弹窗中的 `目标对齐 / 原则对齐 / 需求确认单` 在产品上下文为空时仍必须自动生成初始建议，禁止空白。
8. `reject` / 驳回操作必须即时返回，不允许同步等待模型返工内容导致前端长时间无响应。
9. 本地验收默认入口必须以 `5173` 前端与 `8787` API 为准；静态 `public/generated/*.html` 仅作为交付物预览，不得替代实时页面状态判断。
10. 项目流验收脚本必须与当前鉴权、端口和模板校验契约一致，避免误报“平台不可用”。
11. 项目流脚本在 `PROJECT_ADVANCE_IN_PROGRESS` 慢路径下必须有限重试并可失败返回，禁止无限轮询导致“看起来无响应”。
12. 固定项目验收脚本在目标项目不存在时必须自动创建 fallback 项目继续执行，禁止直接 404 退出。

## 4. 本轮补齐的需求细化（2026-04-02）

### 4.1 新建项目预填链路

- `/api/issues/preview` 必须在 `productContext.goals/principles` 缺失时，基于当前需求语义自动生成：
  - `matchedGoals`
  - `matchedPrinciples`
  - `missionAnchor`
  - `requirementContract`
- 前端弹窗必须把这些字段映射到可编辑草稿中，支持直接确认、局部修改、再创建项目。
- `contextNotes` 必须明确标注“当前产品说明文档不完整，已自动生成初始对齐建议”，避免误导用户认为这些内容来自既有产品基线。

验收标准：
- 使用真实接口请求 `/api/issues/preview` 时，在空产品上下文下仍返回非空 `matchedGoals/matchedPrinciples`。
- 新建项目弹窗中可见并可编辑这些自动预填字段。

### 4.2 审批返工链路

- `POST /api/projects/:id/reject` 必须先完成阶段驳回、任务状态回退、时间轴落点，再异步补充返工说明。
- 驳回后的项目必须立即回到可继续编辑和再次提交的状态。
- 返工说明允许稍后补齐，但不能阻塞用户点击后的响应。
- 手动推进默认单轮超时应兼容慢模型（默认 `180000ms`，可由 `MANUAL_ADVANCE_ATTEMPT_TIMEOUT_MS` 覆盖），降低误判超时导致的空转。

验收标准：
- `reject` 接口在本地环境下应快速返回 `200`，且 `pendingApproval` 从 `true` 变为 `false`。
- 驳回后允许重新提交符合模板的阶段交付稿。

### 4.3 本地验收入口约束

- 本地实时验收入口统一为：
  - 前端：`http://127.0.0.1:5173`
  - API：`http://127.0.0.1:8787`
- `4173` 若存在，只表示对 `apps/web/public` 的静态目录暴露。
- `3001` 若存在，不属于当前 OCC 平台实时验收入口。
- `apps/web/public/generated/*.html` 仅用于展示已生成静态预览产物，不作为判断“当前弹窗/当前项目流状态”的依据。

验收标准：
- 文档、测试与人工验收都以 `5173 + 8787` 组合为准。
- 当静态预览内容与实时页面不一致时，以实时页面和 API 返回为准。

### 4.4 自检脚本环境回收

- 闭环验收、自检、巡检脚本若临时切换运行时配置，仅可作为测试步骤存在。
- 这类脚本在退出前必须恢复原始 `provider / apiBaseUrl / modelName`，禁止把平台长期留在 `scripted` 等非预期模式。

验收标准：
- 执行 `pnpm verify:closure` 前后，`/api/system/runtime` 返回的运行模式保持一致。
- 自检失败时也必须执行配置恢复，不得污染下一轮人工验收。

### 4.5 本地前端可达性与进程托管

- 必须提供前端 dev server 的标准化启停脚本，避免临时命令导致 `5173` 偶发启动后退出。
- 前端托管脚本必须具备：
  - stale PID 自恢复
  - 端口占用探测与 PID 领养
  - 启动健康检查和日志路径提示
- 验收与巡检时必须先确认 `5173 + 8787` 同时可达，再进行项目链路判断。

验收标准：
- `pnpm web:daemon:start` 后 `http://127.0.0.1:5173` 返回 `200`。
- `pnpm web:daemon:status` 能正确区分“进程存在但端点不可达”和“健康可达”。
- `pnpm web:daemon:stop` 可安全停止并清理 PID 文件。

### 4.6 设计交付物必须贴合真实业务

- `DESIGN` 阶段不能再把“有一段 HTML 预览代码”误判成“已经完成设计”。
- 若需求涉及商品、电商、榜单、监控、告警、跟踪、TikTok、Amazon、Temu 等业务词，视觉稿必须直接表现真实业务界面，而不是内部协作流程页。
- 对于跨境爆品选品/跟品场景，视觉稿至少要体现：
  - 爆品榜单或排名
  - 平台来源
  - 爆量指标或监控信号
  - 商品链接
  - 人工跟品动作
- 禁止使用“需求输入 / 多 Agent 协作 / 执行证据回写 / 阶段验收回填”这类模板页面冒充业务设计稿。

验收标准：
- 视觉定稿单页若缺少上述业务信号，应直接卡在模板校验或自动质检，不得进入可审批状态。
- 设计阶段 required actions 应能识别“视觉稿虽然有 HTML，但并非真实业务设计稿”的情况。
- 当前这类修复需要覆盖旧项目返工，避免历史假设计稿继续显示为有效设计。

### 4.7 阶段提交不得“单项即完结”

- 阶段提交接口即使收到 `finalizeApproval=true`，也不能因为“只提交了一份交付物”就直接把阶段推到待审批。
- 只有当前阶段核心交付物全部齐备且均通过模板校验，才允许进入待审批并将阶段任务置为完成。
- 若核心交付物不齐，系统必须自动保持在“持续补充中”，并给出“缺少哪些核心交付物/为什么未通过”的可读提示。

验收标准：
- DESIGN 阶段只提交“设计审查卡”后，`pendingApproval` 必须仍为 `false`，设计任务不得全部 `done`。
- 补齐视觉定稿等核心交付物后再次提交，才可进入待审批。

### 4.8 DEV 阶段必须体现真实开发链路

- DEV 交付（技术方案与选型、Demo 原型说明）不能只停留在静态页面说明。
- 必须提供：
  - 多页面/路由证据
  - 至少 2 个 API 接口证据
  - 数据存储方案（表结构/Schema/迁移）
  - 运行与联调步骤（启动命令、环境变量、验证方法）
  - 至少 2 个真实代码文件路径证据（例如 `apps/.../*.ts`）
  - 联调或验证结论证据（例如 `/health` 检查、HTTP 200、回归结论）
- 跨境爆品场景必须额外体现平台来源（TikTok/Amazon/Temu）和数据更新机制（轮询/Webhook/增量同步）。

验收标准：
- 仅静态单页/mock 数据描述应被模板校验或验收门禁拦截。
- 只有补齐真实数据链路证据后才可通过 DEV 验收。

### 4.9 演示站点链接必须可直接访问

- API 返回的演示站点链接必须是可访问绝对 URL，不能只给相对路径。
- 最终验收报告中“演示站点链接”应优先展示 `访问地址: ...`，避免误导为本地文件路径。
- 前端“打开链接/复制链接”必须统一处理相对路径并输出绝对地址。
- 官方页必须明确标注为“静态交付物汇总页”，不能冒充真实部署站点。

验收标准：
- 点击“打开链接”可直接访问。
- 复制链接后在任意新标签页可独立打开。
- 验收文案明确提示“静态交付物汇总页”。

### 4.10 模板骨架占位必须拦截

- 凡是交付物正文包含以下占位语句，必须直接拒绝提交：
  - `模板章节骨架（自动补齐）`
  - `模板章节骨架（请按模板补全）`
  - `请结合 Agent 输出正文与任务证据补全本节`
- 自动推进与回填逻辑不得再写入上述占位语句作为可审批内容。

验收标准：
- 提交接口返回 `422`，并提示模板骨架占位错误。
- 含占位语句的交付物不得进入待审批/已批准。

## 5. 验收命令

```bash
pnpm --filter @occ/api typecheck
pnpm --filter @occ/api test:routes
pnpm test:smoke
pnpm health:check
pnpm web:daemon:status
node scripts/smoke-project-flow.mjs
pnpm verify:closure
pnpm verify:repeatable:018
```

说明：
- `node scripts/smoke-project-flow.mjs` 用于验证项目创建、推进、审批与最终产物检查主链路。
- `pnpm verify:closure` 用于验证创建、介入、驳回、重提、审批与任务更新闭环。

## 7. 当前已知不足

- OpenClaw 单 agent / batch message 在部分模型会返回 `stopReason=error`，当前闭环验收已降级为 warning，不阻断主链路。
- 静态 `generated` 预览与实时项目前端之间的页面层区分仍可继续加强，减少误判。
