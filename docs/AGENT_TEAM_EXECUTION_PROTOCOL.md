# Agent Team 执行协议

更新时间：2026-04-04

## 目标

把平台里“立项 -> 分析 -> 设计 -> 研发 -> 验收 -> 回填”的零散规则统一成一套适合 Agent Team 协作的执行协议，确保：

1. 长期记忆始终保留，用于后续 Agent 学习与经验复用。
2. 低相关项目记忆、旧模板、默认视觉和历史噪音不会混入当前关键任务。
3. 关键阶段优先走终端 Agent、技能驱动和真实验证，而不是退化成无工具的普通模型直答。
4. 每个阶段都能把事实、假设、决策、交接和验证结果留成可审计记录。

## 一句话原则

长期记忆不能关闭，但默认只允许“当前项目事实 + 高关联历史经验”进入关键执行链路。

## 总体执行模式

平台采用 `Stage-Gated Agile`：

1. `INIT`：立项与项目章程
2. `ANALYSIS`：需求分析、边界澄清、验收标准
3. `DESIGN`：体验方案、结构方案、视觉方案、设计审查
4. `DEV`：架构实现、联调、回归验证
5. `ACCEPT`：验收、回填、归档

核心要求：

1. 每个阶段必须有可审阅交付物。
2. 每个阶段必须有明确门禁，不允许靠“看起来差不多”推进。
3. 每个阶段必须能把结果交给下游 Agent 继续执行，而不是只输出泛泛建议。

## 记忆协议

### 基础规则

1. `memoryEnabled` 默认保持开启。
2. 默认记忆策略统一为 `current_project_or_high_relevance_only`。
3. 长期记忆的作用是学习、对齐和复用经验，不是把旧项目答案直接搬进新项目。

### 允许使用的记忆

1. 当前项目下已经确认的目标、边界、约束、风险、验收标准。
2. 与当前任务强相关的历史经验。
3. 明确属于方法论、质量规则、实现约束的稳定经验。

### 禁止混入的内容

1. 低相关项目的业务背景、页面风格、默认文案。
2. 旧项目官网 Demo、单页视觉模板、客户汇报模板。
3. 与当前任务无关的成功案例、旧结论、过时假设。
4. 未经确认却被写成既定事实的历史记忆。

### 冲突处理

1. 当前 Issue / 当前项目事实优先于长期记忆。
2. 长期记忆与当前输入冲突时，必须显式提示冲突并等待用户或阶段负责人决策。
3. 被判定为模板污染、孤儿项目或低价值旧记忆的内容，进入清理治理流程。

## 模型与执行协议

### 关键阶段原则

1. `ANALYSIS` 的 `ROLE_ANALYST` / `ROLE_PRODUCT` 优先走终端 Agent。
2. `DESIGN` 的 `ROLE_PRODUCT` / `ROLE_DESIGN` 优先走终端 Agent。
3. `DEV` 的 `ROLE_ARCH` / `ROLE_DEV` 优先走终端 Agent。
4. 关键阶段默认不允许直接模型兜底成功写回，必须优先保障真实模型与真实工具链。

### 直接模型阶段原则

1. 非关键阶段可以保留 `direct_model` 执行。
2. 即使是 `direct_model`，也仍然遵守“长期记忆开启，但只限当前项目或高关联经验”的规则。
3. 直接模型输出仍需遵守事实/假设/决策分层，不得省略交接信息。

### 模型强度原则

1. 关键阶段优先使用最强可用真实模型。
2. 设计任务优先使用最强设计模型链，不允许被弱旧配置或历史 session 漂移覆盖。
3. 实现任务优先使用最强编码/推理模型链，必须保留尝试轨迹和回退原因。

## 技能与工具协议

1. 设计类任务优先使用设计技能，而不是直接裸模型输出。
2. 研发类任务优先使用终端、代码编辑、测试与验证工具，而不是只给建议。
3. 如果阶段要求了 `requiredSkills`，则必须先读取并实际使用这些技能。
4. 技能缺失、终端不可用、依赖缺失时，必须显式上报阻塞，不能伪造已完成结果。

## 协作交接协议

每个关键阶段输出都必须包含“协作交接卡”，字段保持固定：

1. `factsConfirmed`
2. `assumptions`
3. `decisions`
4. `handoff`
5. `openQuestions`

使用要求：

1. `factsConfirmed` 只写已确认事实。
2. `assumptions` 只写仍待验证的推断。
3. `decisions` 记录已做取舍及原因。
4. `handoff` 必须能直接作为下游 Agent 的输入。
5. `openQuestions` 用于沉淀尚未关闭的风险与待确认点。

## 技能执行证据协议

关键阶段输出末尾必须追加“技能执行记录”，字段保持固定：

1. `skillsUsed`
2. `reasoningBasis`
3. `artifactsProduced`
4. `verification`

证据要求：

1. `skillsUsed` 记录真实使用的技能或工具。
2. `reasoningBasis` 说明判断依据，而不是空泛结论。
3. `artifactsProduced` 说明已产出的文档、页面、代码或命令结果。
4. `verification` 说明已完成的测试、检查、预览或人工复核。

## 分阶段执行要求

### INIT

1. 产出项目章程。
2. 明确目标、范围、参与角色、阶段负责人与推进规则。
3. 不能把含糊输入直接升级为正式需求。

### ANALYSIS

1. 先做需求澄清、边界判断、价值取舍和风险识别。
2. 输出目标、边界、约束、风险、验收标准、关键里程碑。
3. 分析结果必须可直接交给产品或设计继续执行。

### DESIGN

1. 先明确体验目标、页面范围、内容优先级和关键状态。
2. 再完成结构、视觉、交互和响应式方案。
3. 严禁套用旧项目默认风格、演示页模板和低相关视觉记忆。
4. 输出必须可直接交给研发实现。

### DEV

1. 先沉淀技术方案、接口契约、风险与边界。
2. 再通过真实终端工具完成实现、联调与回归检查。
3. 输出必须包含改动范围、验证结果、遗留风险和 QA 关注点。

### ACCEPT

1. 以可验证结果为准，不以主观印象为准。
2. 完成测试报告、验收结论、产品说明文档回填与长期记忆回填。
3. 只有在 `readyForAcceptance=true` 且必需产物齐全时才能关闭项目。

## 治理与审计协议

1. 每次关键执行都要记录模型尝试、执行模式、阶段原因、记忆策略和验证结果。
2. 一旦出现 `scripted` 或 `degraded` 降级，关键阶段不得按成功结果写回。
3. 上下文卫生治理持续清理孤儿项目记忆、模板污染记忆和陈旧未用模板。

## 推荐使用方式

1. 新项目先按本协议生成项目章程与分析结论。
2. 关键阶段统一走终端 Agent，并强制输出协作交接卡与技能执行记录。
3. 阶段完成后再决定是否推进，而不是边产出边默认通过。
4. 验收通过后再回填产品文档与长期记忆，避免把半成品经验写进长期记忆。
