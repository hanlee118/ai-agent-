# Agent 协作工作台完整需求文档 PRD

## 1. 文档说明

- 文档名称：Agent 协作工作台完整需求文档
- 文档版本：V1.0
- 文档日期：2026-03-25
- 文档用途：用于统一产品设计、UI 设计、前后端研发、测试验收、部署上线与后续迭代
- 当前定位：以 OpenClaw 为真实执行底座，构建一个可观测、可指挥、可审批、可配置、可监控的 Agent 团队协作平台

## 2. 产品愿景

Agent 协作工作台不是一个普通聊天窗口，也不是一个简单任务板，而是一个面向 AI 团队协作的 SaaS 管理平台。用户在平台中管理的不是零散 Prompt，而是一组具备角色分工、能力边界、执行 SOP、人格设定、模型配置和任务责任的数字团队。

平台需要支持用户像管理一个真实项目组织一样，完成以下动作：

- 创建并查看项目
- 看见项目当前进度、风险与交付物
- 看见每个 Agent 正在做什么
- 向单个 Agent 或整个项目团队下达任务
- 在执行前对关键理解和方案进行确认
- 管理 Agent 的模型、SOUL、SOP、职责与状态
- 对整个平台进行运行监控、审计追踪与服务运维

最终目标是让用户能够通过该平台，真正完成从需求提出、分析拆解、设计产出、研发执行、测试验证到交付验收的完整闭环。

## 3. 产品定位

### 3.1 一句话定位

一个基于真实 Agent 团队协作的 AI 项目作战与运营平台。

### 3.2 产品形态

- Web SaaS 管理工作台
- 默认单管理员可用，后续可扩展为组织版
- 以项目为主线，以 Agent 为执行单元，以任务和交付物为落地结果

### 3.3 核心差异点

- 不是只展示聊天记录，而是展示项目、阶段、任务、交付物、Agent 状态和系统健康
- 不是只允许用户直接对话，而是允许用户通过团队管理方式进行编排和监督
- 不是纯自动执行，而是提供“理解确认”和“关键节点审批”机制
- 不是静态 Agent 展示，而是允许配置模型、SOUL、SOP、任务权限和执行策略
- 不是演示数据，而是优先读取真实 OpenClaw 工作区与真实 Agent 会话

## 4. 目标用户

### 4.1 核心用户

- 独立开发者
- AI 产品负责人
- 创始人或业务负责人
- 小团队项目经理
- 希望使用 AI 团队推进多角色协作的人

### 4.2 典型用户诉求

- 我想看到一个项目到底推进到了哪一步
- 我想知道每个 Agent 在做什么，是否卡住
- 我想快速创建项目并分配任务
- 我想在必要时审批，而不是完全黑盒自动执行
- 我想调整某个 Agent 的风格、模型和工作方式
- 我想有一个可上线、可监控、可复盘的平台，而不是单纯演示

## 5. 产品目标

### 5.1 业务目标

- 构建一个真实可用的 Agent 协作工作台
- 实现项目管理、Agent 管理、任务协同、交付追踪和运行监控的一体化
- 以真实 OpenClaw 工作区为数据来源，提升可信度和可操作性

### 5.2 用户目标

- 用户能在 3 分钟内创建一个项目并看到团队开始执行
- 用户能在 10 秒内判断一个项目当前是否健康
- 用户能在 30 秒内定位某个 Agent 当前任务和阻塞点
- 用户能在关键执行前通过选择和确认完成决策，而不是大量填写自由文本

### 5.3 产品原则

- 可观测优先
- 决策清晰优先
- 少填空，多选择
- 项目闭环优先于花哨功能
- 真实执行优先于演示效果

这是平台的核心页面之一，必须单独设计，不能只用 Agent 列表页替代。

目标：

- 用户可以进入某一个 Agent 的专属页面，对该 Agent 进行配置、指挥、确认和持续跟进

页面模块：

- Agent 头部信息区
- 模型配置区
- 执行策略区
- SOUL 编辑区
- SOP 编辑区
- 当前任务区
- 历史任务区
- 最近会话区
- 指令下达区
- 理解确认区
- 执行状态区

#### 10.7.1 Agent 基础信息

需要展示：

- Agent 名称
- Agent ID
- 角色
- 介绍信息
- 擅长事项
- 当前状态
- 当前模型
- 最近活跃时间
- 当前项目归属

#### 10.7.2 模型选择与切换

用户可以在 Agent 单独页面中：

- 查看该 Agent 当前使用的模型
- 查看该 Agent 可用模型列表
- 切换模型
- 查看模型能力标签，例如速度优先、推理优先、成本优先、多模态优先
- 设置默认模型
- 设置备用模型
- 查看模型切换记录

模型切换需要具备：

- 切换前提醒
- 切换后生效反馈
- 不可用模型禁用态
- 失败回滚提示

#### 10.7.3 指令下达与接单机制

用户可以在 Agent 单独页面中，向该 Agent 下达任务或工作指令。

交互要求：

- 支持一个专门的对话 / 指令面板
- 支持快速下达“请分析”“请拆解”“请执行”“请汇报”“请修复”“请设计”等常用命令
- 支持用户自由输入补充说明
- 支持结构化任务单

系统在 Agent 真正开始执行前，必须先让 Agent 对用户指令进行理解与拆解，然后由用户决定是否继续执行。

#### 10.7.4 执行前理解确认机制

当用户向 Agent 下达任务后，Agent 不能直接盲目执行，而是需要先返回一张“理解确认卡”。

理解确认卡至少包含：

- 我理解你的目标是什么
- 我准备怎么做
- 我预计拆成哪些步骤
- 我认为的风险和疑问
- 我建议的执行路径
- 是否需要你确认关键点

用户确认方式以选择和确认动作为主，不以填空为主。

页面需要支持的确认动作：

- 确认并执行
- 修改后再理解
- 只做分析，不执行
- 更换模型后重试
- 转交其他 Agent
- 取消本次任务

#### 10.7.5 直接由你决定模式

Agent 单独页面必须支持一个策略开关：

- 默认模式：执行前需要确认
- 自主模式：直接由你决定

当用户开启“直接由你决定”后：

- 该 Agent 在收到任务后可自行拆解、执行、推进
- 只在重大风险、权限不足、依赖缺失、成本超限或策略冲突时再请求人工确认
- 平台需要明确显示当前 Agent 处于自主执行模式

#### 10.7.6 确认交互形式

确认方式需要以可点击选择项和确认按钮为主，例如：

- 单选项
- 多选项
- 推荐选项
- 确认按钮
- 驳回按钮
- 延后处理按钮

要避免让用户频繁填写大段文本。

#### 10.7.7 当前任务与执行状态

页面需要展示：

- 当前手头任务
- 任务优先级
- 任务进度
- 当前阻塞
- 最近一次执行结果
- 最近一次确认结论
- 是否等待用户

#### 10.7.8 SOUL / SOP 编辑

用户可以在 Agent 单独页面直接编辑：

- SOUL：人格、风格、原则、沟通方式
- SOP：标准工作流程、交付规范、检查清单、升级机制

要求：

- 直接保存
- 可回写真实文件
- 支持查看最后更新时间
- 支持区分已存在与待创建

### 10.8 系统运行中心

目标：

- 让用户知道平台本身和 Agent 运行环境是否稳定

## 11. 核心流程设计

### 11.1 创建项目流程

1. 用户输入项目目标
2. 系统生成需求理解卡
3. 用户确认理解结果
4. 系统创建项目
5. 系统推荐团队与初始任务
6. 项目进入执行态

### 11.2 项目推进流程

1. Agent 根据当前阶段执行任务
2. 更新任务进度与交付物
3. 若进入审批节点，则生成确认单
4. 用户确认后进入下一步
5. 完成后沉淀交付物和时间线

### 11.3 单个 Agent 接单流程

1. 用户进入 Agent 单独页面
2. 选择模型或保持当前模型
3. 输入任务或选择快捷指令
4. Agent 先输出理解确认卡
5. 用户点击“确认并执行”或其他选项
6. Agent 开始执行
7. 页面持续展示执行进度、回复和结果

### 11.4 自主执行流程

1. 用户开启“直接由你决定”
2. 用户向 Agent 下达目标
3. Agent 自主完成分析、拆解与执行
4. 仅在关键风险节点请求人工确认
5. 最终输出结果与过程记录

### 11.5 项目广播流程

1. 用户在项目页输入统一指令
2. 系统识别该项目相关 Agent
3. 向相关 Agent 批量下发消息
4. 收集回复结果
5. 展示发送成功、失败、未响应列表

## 12. 交互设计要求

### 12.1 交互原则

- 少填空，多选择
- 先理解，再执行
- 先提示风险，再允许继续
- 重要动作必须有反馈
- 状态必须可视化

### 12.2 关键交互规范

- 危险动作需要二次确认
- 模型切换需要成功或失败反馈
- 回写真实文件必须提示写入结果
- 长时任务必须有 loading、阶段提示和结果反馈
- Agent 等待用户确认时需要明显高亮

### 12.3 中英文切换

平台必须支持中英文切换，要求：

- 全局可切换
- 文案统一
- 页面标题、按钮、状态、说明文案均可切换
- 默认跟随用户设置并持久化

- 不能像简单后台表单页，也不能像单页聊天工具
- 强调卡片层级、状态色、信息密度与高级感

### 13.2 设计关键词

- 专业
- 清晰
- 高级
- 可观测
- 可指挥
- 有秩序感

### 13.3 布局要求

- 左侧主导航
- 顶部工作区信息与全局操作
- 主内容区按模块分组
- 项目页和 Agent 页采用控制台式多区域布局
- 移动端保留核心能力，支持查看项目、Agent、任务和确认操作

### 13.4 视觉要求

- 卡片可扫读

- 支持运行时模型配置
- 支持健康检查与审计日志

### 14.3 前端能力要求

- 多页面管理台
- 实时刷新与轮询
- 国际化支持
- 表单与确认流组件化
- 支持任务、项目、Agent 三级视图切换

### 14.4 数据要求

- 当前可用 SQLite 或轻量数据库
- 后续应可迁移到 PostgreSQL
- 需支持审计数据、配置数据、任务数据和缓存数据的拆分

## 15. 非功能需求

### 15.1 可用性

- 常用页面 3 秒内可见首屏
- 关键接口失败时有明确错误提示
- 页面无数据时有可理解空态

### 15.2 安全性

- 至少具备管理员登录保护
- 关键配置加密存储
- 审计日志不可静默篡改

### 15.3 可维护性

- 前后端代码模块清晰
- 类型统一
- 页面与组件职责明确
- 配置集中管理

### 15.4 可观测性

- 服务健康检查
- Runtime 校验
- Agent 心跳监控
- 错误日志
- 审计日志

## 16. 验收标准

### 16.1 项目维度验收

- 可以看到真实 OpenClaw 项目列表
- 可以进入某个项目查看任务、交付物、Agent 和时间线
- 可以对任务进行回写
- 可以生成项目报告

### 16.2 Agent 维度验收

- 可以看到完整 Agent 列表，包含 jeremy
- 可以看到每个 Agent 的介绍、状态、负载与当前任务
- 可以进入 Agent 单独页面
- 可以切换模型
- 可以编辑 SOUL / SOP
- 可以向 Agent 下发任务
- Agent 会先返回理解确认卡
- 用户可以确认后再执行
- 可以切换到“直接由你决定”模式

### 16.3 平台维度验收

- 支持中英文切换
- 支持登录保护
- 支持系统健康检查
- 支持操作审计
- 页面结构符合 SaaS 管理台逻辑

## 17. 成功指标

- 用户能清楚知道每个 Agent 当前在做什么
- 用户能通过选择与确认完成关键决策
- 用户能通过平台真实推进至少一个项目到交付
- 用户能信任平台作为 Agent 团队作战中台持续使用

## 19. 结论

这份 PRD 的核心不是做一个“能聊天的 Agent 页面”，而是建设一个真正面向 Agent 团队协作的工作台。平台必须同时满足四件事：

- 能展示真实项目
- 能展示真实 Agent
- 能真正下达任务并推动执行
- 能在关键节点让用户用最轻的方式完成确认和控制

后续所有 UI 设计、技术架构设计、前端页面设计、接口设计、测试用例与上线验收，都应基于本文件继续展开。
