# 交付物专业格式标准（Project Lifecycle v1.0）

## 目标
- 统一项目从创建到实施结果的文档质量门槛。
- 让每份交付物都可被机器校验、可被人复核、可被下阶段直接消费。
- 降低 Agent / 模型输出中的幻觉、占位文本、证据缺失问题。

## 通用硬要求（全部交付物）
- 必须使用 Markdown 二级标题（`##`）组织正文。
- 必须包含 `## 验收检查清单`，且命中该交付物验收条目。
- 禁止占位词（如 `TODO`、`TBD`、`待补充`、`占位`、`xxx`）。
- 正文长度不得少于 180 字。
- 结论必须带证据，不允许只给口号式总结。

## 分交付物专业格式要求

### 1) 需求分析文档（`requirements_prd`）
- 必含章节：
  - `## 事实依据与来源（Source of Truth）`
  - `## 需求追踪矩阵（目标-功能-验收）`
  - `## 决策记录（Decision Log）`
- 证据要求：事实来源、可量化指标、非目标边界。
- 结构要求：至少 12 条条目，且至少 1 个 Markdown 表格。

### 2) 项目排期方案（`schedule`）
- 必含章节：
  - `## 里程碑基线（日期 / Owner / Exit Criteria）`
  - `## 关键路径与依赖矩阵`
  - `## 变更控制与升级机制`
- 证据要求：里程碑日期、Owner/RACI、延期升级规则。
- 结构要求：至少 10 条条目，且至少 1 个 Markdown 表格。

### 3) 设计审查卡（`design_review`）
- 必含章节：
  - `## 设计决策记录`
  - `## 可访问性检查结果（WCAG）`
  - `## 审查结论与整改项`
- 证据要求：WCAG/可访问性证据、明确审查结论、Figma 或可渲染预览证据。
- 结构要求：至少 8 条条目，且至少 1 个 Markdown 表格。

### 4) 视觉定稿单页（`visual_mockup`）
- 必含章节：
  - `## 设计 Token 映射（色彩 / 字体 / 间距）`
  - `## 状态反馈矩阵（默认 / 悬停 / 禁用 / 错误）`
  - `## 响应式断点策略`
- 证据要求：Token 映射、状态定义、可渲染 HTML 预览。
- 结构要求：至少 8 条条目，且至少 1 个 Markdown 表格。

### 5) 技术方案与选型（`implementation_word`）
- 必含章节：
  - `## 架构决策记录（ADR）`
  - `## 接口契约矩阵（字段 / 约束 / 错误码）`
  - `## 发布与回滚演练计划`
- 证据要求：接口契约、数据结构/迁移、回滚策略。
- 结构要求：至少 10 条条目，且至少 1 个 Markdown 表格。

### 6) 实现结果说明（`implementation_result`）
- 必含章节：
  - `## 变更证据（Commit / 文件）`
  - `## 验证命令与结果`
  - `## 风险回归与残留问题`
- 证据要求：至少 2 个真实代码文件路径、验证命令与结果、版本追踪信息（Commit/MR）。
- 结构要求：至少 10 条条目。

### 7) 运行地址与部署说明（`runtime_delivery`）
- 必含章节：
  - `## 环境变量清单（必填 / 可选）`
  - `## 部署检查清单（Pre-flight / Post-check）`
  - `## 回滚触发条件与处理流程`
- 证据要求：运行地址、环境变量、部署命令。
- 结构要求：至少 8 条条目，且至少 1 个 Markdown 表格。

### 8) 测试报告（`test_report`）
- 必含章节：
  - `## 测试覆盖矩阵（需求 / 用例 / 结果）`
  - `## 缺陷分级与处置`
  - `## 发布建议与风险签收`
- 证据要求：测试用例编号、缺陷分级、结果统计。
- 结构要求：至少 8 条条目，且至少 1 个 Markdown 表格。

### 9) 产品说明文档回填（`product_backfill`）
- 必含章节：
  - `## 需求-交付映射表`
  - `## 版本变更记录`
  - `## 已确认事实与待决策项`
- 证据要求：需求映射、版本记录、待决策风险项。
- 结构要求：至少 6 条条目，且至少 1 个 Markdown 表格。

## 执行与门禁
- 文档提交时执行模板门禁：缺章节/缺证据/占位语句将直接拒绝。
- 阶段审批前执行模板预检：核心交付物未达标则阻断推进。
- 生命周期质量审计接口用于全阶段复核：`GET /api/projects/:id/lifecycle-quality-audit`。

## 结果解释建议
- `pass=true`: 当前阶段执行与核心交付物满足推进标准。
- `pass=false`: 优先处理 `issues` 中的“缺证据 / 缺章节 / 角色无真实执行记录”。
- `professionalChecks`: 每个证据项都可定位为可修复动作，而不是模糊“质量不足”。
